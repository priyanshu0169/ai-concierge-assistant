# ShopSage

A reusable, configuration-driven AI shopping assistant platform for Magento Commerce.

ShopSage is a **platform**, not a chatbot for one store. The same codebase serves any Magento
storefront: everything store-specific — company name, assistant name, prompts, branding, enabled
capabilities, retrieval tuning — lives in a JSON site profile, never in source. No company name
appears anywhere in this repository.

> **Current status: Stage 9 of 10 complete — a working, embeddable assistant that can answer about
> products and orders, and change a basket only with the customer's explicit consent.**
> A question arriving at `POST /v1/chat` is embedded, retrieved from the store's knowledge base, and
> answered with citations. Verified end to end against a real LLM gateway, a real embedding gateway and
> real Qdrant: _"How long do I have to return something?"_ → _"You have thirty days from the delivery
> date to return unopened items…"_ with three sources, while a question the corpus cannot answer returns
> the store's no-answer message and **no** citations.
>
> Retrieval reaches the model as a **tool** it chooses to call, not as a pre-built prompt. Stage 9a is
> the test of that claim: four commerce tools arrived as four table entries with **no change to the
> conversation loop**. Conversation history works —
> a follow-up of _"And internationally?"_ resolves correctly — though it is held in process memory until
> a durable store lands.
>
> **Stage 7a adds streaming.** `POST /v1/chat/stream` delivers the same turn as it happens: the
> conversation id at 70ms, "searching the help centre" while retrieval runs, then the answer token by
> token. Total latency is unchanged at ~5s — the buffered endpoint just spends four of those seconds
> showing nothing.
>
> **Stage 7b makes it scale.** Conversation history moved into a shared store, so two replicas answer the
> same conversation consistently — verified by asking on one process and recalling on another. In
> production the backend now refuses to boot without being told which store to use, because guessing
> wrong is invisible until customers notice the assistant forgetting things at random.
>
> **Stage 7c adds limits.** A token bucket per client on `/v1`, plus a separate ceiling on how many
> answers can be streaming at once — a request is spent, a stream is held, and one number cannot express
> both. A client over its rate gets `429` with `Retry-After`; a service at capacity gets `503`, because
> those are not the same thing and a customer should not be blamed for the second.
>
> **Stage 7d adds authentication.** Magento mints a short-lived ES256 token; ShopSage verifies it against
> a cached key set without calling Magento per request. The token's subject is a **pseudonym** — ShopSage
> never learns who the customer is, and a tool needing real identity will forward the token to Magento,
> which minted it. The contract was written and reviewed before any code:
> [Proposal 0001](docs/proposals/0001-assistant-session-token.md).
>
> **Stage 8 adds the widget.** A native custom element in a shadow root — **23 kB minified, zero
> dependencies, one `<script>` tag** on any website. It renders a model's answer as **DOM nodes,
> never through `innerHTML`**, because that text is untrusted input. Everything store-specific
> arrives from `GET /v1/config` at run time, so nothing in the bundle names Magento and the same
> bytes serve any future platform.
>
> **Stage 9a adds commerce reads.** Products, comparisons, recommendations and order tracking, read live
> from the store's connector over HTTP — the Magento module lives in its own repository and ShopSage
> consumes a contract ([Proposal 0002](docs/proposals/0002-commerce-connector-contract.md), accepted).
> Verified against a checked-in **reference connector** that is a runnable form of that contract.
>
> The rule that shapes it: **the assistant may quote a price and may never compute one.** No totals, no
> discounts, no differences — the one thing this project consistently refuses to publish is a
> plausible-looking number generated by a language model, and money is where that matters most. It is
> enforced in the prompt, in every tool result, and by there being no tool shaped like a calculator. It
> is a **mitigation, not a guarantee**, and
> [ADR 0028](docs/adr/0028-commerce-reads-behind-one-adapter.md) says exactly where the limit is —
> including the question that defeated an earlier version of the rule.
>
> Also in 9a, and applying to every conversation whether commerce is on or not: **personal data is
> removed from conversation history before it is stored.** Email addresses, card numbers and phone
> numbers, on both sides of a turn. The customer still sees what they typed; only the copy that outlives
> the turn is reduced.
>
> **Stage 9b adds the basket, behind consent.** `addToCart` and `applyCoupon` **cannot change anything**:
> they prepare a proposal, the customer clicks a confirmation, and a separate endpoint executes it. The
> model is out of the commit path as a property of what it can reach — the tools have no access to the
> write client at all — and there is deliberately no endpoint a client could use to _ask_ for a basket
> change, only to agree to one.
>
> The sentence a customer consents to is written by ShopSage from connector data, not by the model, and
> rendered as text rather than markdown. Consumption is take-once and atomic, so a double-tapped button
> has exactly one winner. Confirmed against a live stack: two of a £120.00 jacket prepared, confirmed,
> and the **connector** returned £240.00 — nothing on this side multiplied anything.
> [ADR 0029](docs/adr/0029-cart-changes-need-a-confirmed-proposal.md).
>
> **Stage 10a adds metrics**, and the gap it closes is worth stating precisely: an assistant returning the
> store's no-answer message to every question is indistinguishable from a healthy one if all you have is
> HTTP status codes — both are `200`. `GET /metrics` publishes the Prometheus exposition format with **no
> dependency**, and instrumentation is decorators around the ports the domain already declared, so
> `assistant-core` imports nothing about metrics and no test double changed.
>
> The first live scrape earned its keep: three chat turns, all `200`, all **ungrounded**, with a retrieval
> failure behind them. It also turned Stage 7a's argument into a number — 2.5s to first token against 3.7s
> of a buffered turn showing nothing.
> [ADR 0030](docs/adr/0030-metrics-as-port-decorators.md).
>
> **Not yet:** CI and coverage gating (10b), the retrieval evaluation suite (10c), and alerting, deployment
> manifests and load testing (10d). See [docs/Roadmap.md](docs/Roadmap.md).

## Architecture at a glance

```
Magento storefront
      │  (widget, cross-origin HTTPS)
      ▼
ShopSage backend  ── rag-backend ......... HTTP delivery only
      │
      ▼
   assistant-core ...................... business logic, framework-free
      │                                  declares ports; imports no adapter
      ├── LanguageModel port ─────────▶ llm-client ......... any OpenAI-compatible gateway
      ├── KnowledgeRetriever port ────▶ embeddings-client + vector-repository (Qdrant)
      ├── ConversationStore port ─────▶ in-memory (dev) or Redis, by configuration
      └── CommerceCatalogue port ─────▶ magento-client ..... HTTP only, no Magento logic
```

The domain declares what it needs; `rag-backend` supplies it. Note that retrieval is **one** port, not
two: `assistant-core` never learns that answering a question involves an embedding model or a vector
index, which is what lets a reranker or hybrid search arrive without touching business logic.

Magento business logic lives in a **separate repository** as a Magento module. ShopSage only ever
consumes the HTTP APIs that module exposes. See [docs/Architecture.md](docs/Architecture.md).

## Quick start

```bash
git clone <repository-url> shopsage
cd shopsage
cp .env.example .env
```

Set three values in `.env` — the backend will not start without them:

```ini
LLM_API_KEY=…
LLM_BASE_URL=https://your-gateway/v1    # any OpenAI-compatible endpoint
LLM_MODEL=…
```

```bash
docker compose up --build
```

Then:

```bash
curl http://localhost:3000/health         # liveness
curl http://localhost:3000/health/ready   # readiness, per dependency
curl http://localhost:3000/health/info    # which site profile is loaded

curl -XPOST http://localhost:3000/v1/chat \
  -H 'content-type: application/json' \
  -d '{"message":"What is your return policy?"}'
```

An assistant with no model cannot answer anything, so a missing credential is a **boot failure** naming
every variable that is absent — not a 502 on a customer's first question. See
[ADR 0013](docs/adr/0013-required-config-per-entry-point.md).

`/health/ready` reports `degraded` until Qdrant and the embeddings service are up. On first run the
embeddings service downloads model weights (~2.2 GB for `BAAI/bge-m3`), which takes several minutes.
This is expected and does not block the backend.

`bge-m3` needs real memory to warm up — budget **at least 4 GB for that container alone**, and expect it
to fail to start rather than run slowly if it is short. On a smaller machine, switch to
`BAAI/bge-small-en-v1.5` with `EMBEDDING_DIMENSIONS=384`. See [docs/Docker.md](docs/Docker.md).

## Running without Docker

```bash
npm install
npm run dev     # loads .env via Node's --env-file-if-exists; no dotenv dependency
```

Requires Node.js >= 22.11, and the same three `LLM_*` variables. `/health/ready` will report `degraded`
unless Qdrant and the embeddings service are reachable — start them with
`docker compose up shopsage-qdrant shopsage-embeddings`.

Every entry point meant to be run directly with `node` — the backend, and the ingestion and preview CLIs
below — takes its configuration from `process.env` and nothing else, exactly like the Docker image does.
The `npm run` scripts add `--env-file-if-exists=.env`, Node's own environment-file flag, so a local `.env`
loads without a `dotenv` dependency and without the composition roots knowing a file was involved. Calling
a script's underlying `node …` command directly, without going through `npm run`, needs the flag added by
hand or the variables exported some other way — Docker never needs either, since Compose injects them
straight into the container's environment and no `.env` file exists inside the image at all.

The LLM gateway is deliberately **not** in `/health/ready`: it is a metered third party, and a readiness
check that bills per call, once per instance every few seconds, is a bill nobody agreed to.

## Quality gates

```bash
npm run verify     # format check + lint + typecheck + tests
```

| Command             | Purpose                                                        |
| ------------------- | -------------------------------------------------------------- |
| `npm test`          | Unit and HTTP integration tests (`node:test`, no test runner)  |
| `npm run typecheck` | `tsc --noEmit` over JSDoc — no build step, no `.ts` sources    |
| `npm run lint`      | ESLint, including the structural limits of the coding standard |
| `npm run format`    | Prettier                                                       |

The codebase is JavaScript with ES modules and JSDoc. TypeScript is used only as a type checker;
nothing is compiled. See [ADR 0002](docs/adr/0002-javascript-with-jsdoc-type-checking.md).

## Filling the knowledge base

Ingestion is a **batch job**, not part of a request. A crawl takes minutes; a backend that blocked on
one would never become ready.

```bash
# Dry run: what would a crawl produce? Embeds nothing, stores nothing.
npm run preview -- --source <id> --limit 5

# Crawl, chunk, embed and store. Re-running an unchanged corpus embeds nothing.
npm run ingest -- [--source <id>] [--force] [--no-prune]

# Measure retrieval against config/golden-questions.json. Non-zero exit on any failure.
npm run evaluate
```

Each forwards to the file its name suggests (`node --env-file-if-exists=.env packages/….js`) — the `--`
before the flags is npm's own separator, so `--source` reaches the script instead of being read as an
`npm` option.

What to crawl lives entirely in the site profile's `content.sources[]` — seeds, sitemaps, include and
exclude patterns, depth, rate, per-path classification. No path, host or store name appears in the
scraper. See [docs/Configuration.md](docs/Configuration.md) and
[ADR 0017](docs/adr/0017-crawl-behaviour-is-site-profile-data.md).

**The backend will not report ready until this has run at least once.** `/health/ready` checks that the
configured collection exists, because a backend with no knowledge base cannot answer anything and should
not receive traffic.

## Asking a question

```bash
curl -XPOST localhost:3000/v1/chat -H 'content-type: application/json' \
  -d '{"message":"How long do I have to return something?"}'
```

```json
{
  "conversationId": "c_a1fecd4e898b41f98e3a8f2076b5cbf1",
  "messageId": "m_3e4fc705f94f4f4c9febf2b44b52c602",
  "answer": "You have thirty days from the delivery date to return unopened items for a full refund…",
  "sources": [{ "title": "Returns policy", "url": "https://example.com/help/returns" }],
  "finishReason": "stop"
}
```

Pass `conversationId` back on the next request to continue the conversation. An empty `sources` array
means the answer was **not** grounded in store content — either nothing was relevant enough, or the model
chose not to search — which is a signal worth surfacing to whoever reads the answer.

Expect around 5 seconds for a grounded answer: two gateway calls (decide to search, then answer from what
was found) plus an embedding call.

**For anything a person is watching, stream it instead:**

```bash
curl -N -XPOST localhost:3000/v1/chat/stream -H 'content-type: application/json' \
  -d '{"message":"How long do I have to return something?"}'
```

```
event: start   data: {"conversationId":"c_0e05d1cd…","messageId":"m_a6eddc27…"}
event: tool    data: {"name":"searchKnowledge","phase":"started"}
event: tool    data: {"name":"searchKnowledge","phase":"finished"}
event: delta   data: {"text":"You"}
event: delta   data: {"text":" have thirty days"}
event: done    data: { …the same body POST /v1/chat returns… }
```

Same total latency, completely different wait: the id arrives at 70ms and the `tool` events fill the ~4
seconds before the first token. `done.answer` is authoritative — deltas are a preview of it, and a model
that returns no prose sends zero deltas with the store's no-answer message only in `done`. Full protocol
in [docs/API.md](docs/API.md), rationale in
[ADR 0023](docs/adr/0023-streaming-delivery-over-sse.md).

## Embedding the widget

```html
<script
  src="https://cdn.example.com/shopsage.js"
  data-backend-url="https://assistant.example.com"
  data-token-url="/assistant/session"
  defer
></script>
```

That is the whole integration. A native custom element in a shadow root: no framework, no runtime
imposed on the page, **23 kB minified with zero dependencies**.

```bash
npm run build -w @shopsage/widget   # dist/shopsage.js and dist/shopsage.min.js
```

Theme it from the host page — custom properties are the only thing that crosses a shadow
boundary, which is exactly the point:

```css
shopsage-widget {
  --shopsage-accent: #b91c1c;
}
```

A model's answer is rendered as **DOM nodes, never through `innerHTML`** — that text is untrusted
input, and building nodes makes injection structurally impossible rather than a sanitiser away.
See [docs/Widget.md](docs/Widget.md).

## Configuration

Two sources, with a hard boundary between them:

| Source                     | Holds                                          | Example                         |
| -------------------------- | ---------------------------------------------- | ------------------------------- |
| Environment variables      | Infrastructure and **secrets**                 | `LLM_API_KEY`, `QDRANT_URL`     |
| `config/site-profile.json` | Store behaviour, branding, copy, feature flags | `assistantName`, `systemPrompt` |

A secret must never appear in a site profile: profiles are non-secret deployment data, and their
contents are partly served to browsers. See [docs/Configuration.md](docs/Configuration.md) and
[ADR 0004](docs/adr/0004-configuration-boundary.md).

The boundary is why swapping gateways is not a code change. `LLM_API_KEY`, `LLM_BASE_URL` and
`LLM_MODEL` are read by exactly one package, and nothing else in the codebase learns which provider,
model or endpoint is in use — not even that a gateway exists.
